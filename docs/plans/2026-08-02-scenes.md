# L2 scenes — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give cml a layer between a single message and a standing rule — one summary per real working session — and make it retrievable.

**Architecture:** One `scene` row per session with five or more conversation rows, written by the existing curator path under a new rubric. Scenes are a **retrievable object**: they answer `cml search`, and `recall()` injects a matching scene as one line of its three-line briefing. They are **not** a ranking signal over `mem` rowids — see below.

**Tech Stack:** C++20, sqlite3 FTS5, simdjson, CMake, the DeepSeek endpoint already configured at `distill.cpp:29`.

**Spec:** `docs/design/layering-and-offload.md`

## Global Constraints

- **300 lines per source file, hard.** `recall.cpp` is 306 — Task 1 exists because of it.
- `-Wall -Wextra -Wpedantic -Werror`. C++20. `-j2` on builds, never higher — 2 cores, ~800 MB free.
- Hook subcommands exit 0 on every path (`main.cpp:60-61`).
- FTS5 definitions must not drift: `tokenize='porter unicode61'`, metadata as `UNINDEXED` (`db.cpp:147-157`).
- Curator calls cost real money. Calibrate on 20 before spending the rest.
- **Sequence after the offload work commits.** Both plans touch `cpp/CMakeLists.txt`; staging another agent's uncommitted files into a scenes commit is a real hazard on this branch.
- Build: `cmake -S cpp -B cpp/build && cmake --build cpp/build -j2` · Test: `./cpp/build/cml_selftest`

## What changed, and why the re-rank is gone

The original plan made scenes a re-ranking signal gated on `cml eval` recall@3 rising above 19.7%. Pre-implementation validation measured that gate against the live index and it **cannot be passed by anything**:

| k | recall@k |
|---|---|
| 3 | **15.8%** — the real baseline today, not 19.7% |
| 40 | **19.6%** — the ceiling of any reordering |

`retrieve()` reranks a pool hard-capped at `kCandidates = 40` (`recall.cpp:46` → `search.cpp:76`), so `recall@40` bounds every possible re-rank. The spec's 19.7% sits above it: a perfect oracle promoting the answer to rank 1 whenever it exists in the pool still fails. Widening the pool does not rescue it (100 → 21.9%, 400 → 22.2%) — the answer is simply not in the BM25 set for ~80% of questions. Real headroom is +3.8 points, twelve questions of 311, against **49 currently-hitting questions that a wrong promotion can demote**.

The measurement also leaks: a scene is written from its own session's rows, and eval's ground truth is the next turn *in that same session*, so a scene match would lift its own answer for a reason that cannot occur in production. 96.1% of sampled pairs sit in an eligible session. The escape hatch does not exist — `--cross-session` excludes the session the answer lives in and therefore measures 0.0%, always (a pre-existing `eval.cpp` defect worth deleting or fixing separately).

So scenes are built for what they can actually do, and measured by something that is not recall@3.

## Non-goals

- Re-ranking `mem` rowids. Above.
- Auto-generated L3 persona. Permanently — `MEMORY.md` / `CLAUDE.md` are the owner's standing orders.
- Sub-session episode splitting. One scene per session is the lazy version.
- Team, ACL, sharing. One machine, one user.

### Task 2: The `scene` table

**One FTS5 virtual table, not a table plus a mirror.** `mem` and `work` are FTS5-only with metadata as `UNINDEXED` (`db.cpp:147-157`); nothing in this schema keeps a real table and an index in sync, and there are no triggers. Matching that convention halves the write path. The lost PRIMARY KEY costs nothing — `build_scenes` already skips sessions present in `scene`.

- [ ] **Step 1: Append to the `db.exec` block in `open_db()`**

```cpp
        // L2: one row per session worth summarising. Additive — the only destructive path
        // in this function keys on `mem`'s column list (db.cpp:126) and cannot be tripped
        // by adding tables, exactly as `hints` and `recalled` were added.
        "CREATE VIRTUAL TABLE IF NOT EXISTS scene USING fts5("
        "    title, summary, outcome, session UNINDEXED, project UNINDEXED,"
        "    ts_start UNINDEXED, ts_end UNINDEXED, n_rows UNINDEXED,"
        "    tokenize='porter unicode61');"
```

- [ ] **Step 2: Write the test — in a temp `CML_HOME`, never the real index**

No existing selftest opens a database (verified across all nine files in `cpp/src/selftest/`). This is the first, so it goes in its own `cpp/src/selftest/scene.cpp` with `suite_scene()`. `data_dir()` reads `getenv("CML_HOME")` on every call (`paths.cpp:14-19`), so the override is sound.

```cpp
void test_scene_schema_is_additive() {
    const auto tmp = std::filesystem::temp_directory_path() / "cml-selftest-scene";
    std::filesystem::remove_all(tmp);
    std::filesystem::create_directories(tmp);
    setenv("CML_HOME", tmp.c_str(), 1);
    {
        cml::Db db = cml::open_db();
        ok(static_cast<bool>(db), "index opens");
        ok(db.scalar("SELECT count(*) FROM sqlite_master WHERE name='scene'") == 1,
           "scene table created");
        ok(db.exec("INSERT INTO mem(text,asks,role,project,session,ts,file)"
                   " VALUES('hello','','user','p','s','2026-01-01','f')"),
           "mem still writable alongside it");
    }
    {
        cml::Db db = cml::open_db();  // reopening must not rebuild
        ok(db.scalar("SELECT count(*) FROM mem") == 1, "additive means additive");
    }
    unsetenv("CML_HOME");
    std::filesystem::remove_all(tmp);
}
```

Declare `suite_scene()` in `harness.hpp`, call it from `selftest.cpp`, add the file to `cml_selftest`.

- [ ] **Step 4: Write the prompt**

> You are given one working session between a developer and an assistant. Produce a title, a summary of two to three sentences, and an outcome of exactly `solved`, `abandoned`, or `ongoing`.
>
> The summary must state what was actually learned or decided and why — the mechanism, the root cause, the rule that came out of it. It must NOT be an activity log. "Worked on the parser", "debugged the hook", "made several changes" are failures: they describe that time passed, not what is now known. If the session established nothing worth knowing months from now, say so in one sentence and set outcome to `abandoned`.
>
> Reply with a JSON object: `{"scenes": [{"id": <id>, "title": ..., "summary": ..., "outcome": ...}]}`. No prose outside it.

- [ ] **Step 5: Implement `parse_scenes`** in `distillwire.cpp`, reading `parsed["scenes"]`. Mirror `parse_verdicts`' simdjson-on-padded-string shape. **There is no fenced-code-block tolerance in `parse_verdicts`** (`distillwire.cpp:147-153`) — do not write code claiming to mirror one. A separate parser is genuinely required: `parse_verdicts` demands `id` *and* `keep` and silently skips rows missing either.

### Task 4: `cml distill --scenes`, calibrated on 20

**Files:** create `cpp/src/scenes.cpp`, `cpp/src/scenes.hpp`; modify `distill.cpp` (flag), `main.cpp` (usage), `CMakeLists.txt`.

**Interface:** `std::size_t build_scenes(Db& db, const std::string& key, std::optional<std::size_t> cap, bool verbose);` — returns scenes written, skips sessions already in `scene`.

- [ ] **Step 1: Eligibility — with the role filter**

```sql
SELECT session, project, min(ts), max(ts), count(*) n FROM mem
 WHERE session != '' AND role IN ('user','assistant','summary')
 GROUP BY session HAVING n >= 5
```

The role filter matters: without it the query includes `memory` and `wiki` rows (194 in the index), which are curated note files, not conversation. That is one session of 77 today — a scene over fragments of `MEMORY.md`. `stats()` already filters this way (`report.cpp:63-64`). Expect **76 sessions**; 209 of 315 hold a single row and get no scene.

- [ ] **Step 2: Digest — keep the ending, not just the opening**

Rows in `ts` order, gist where `distilled.gist` is non-empty, else `substr(text,1,300)`.

**When over ~6,000 chars, keep the first 2 rows and the last N — never a prefix.** Measured: digests run median 4,460 chars, p90 17,575, max 67,395, and **27 of 76 exceed the cap**. Those 27 are the long, substantial sessions a scene is most for, and `outcome` (`solved`/`abandoned`/`ongoing`) is determined by how a session *ended*. A prefix cap judges the 282-row session on its first 9% and asks it what the outcome was.

- [ ] **Step 3: Batch 4, not 20**

`judge_batch` runs `curl --max-time 90` (`distillwire.cpp:94-98`) and `distill_new` batches at `kBatch = 20` (`distill.cpp:30`). Twenty 6 KB digests is a ~120 KB request producing 20 summaries — it will not finish in 90 s. Use 4–5 sessions per call. `build_judge_request` itself has no length cap, so the builder needs no change.

- [ ] **Step 4: Add the `--scenes` flag** to `distill()`, beside `--all` and `--limit`.

- [ ] **Step 5: Calibrate on 20 and READ them**


- [ ] **Step 2: The briefing line.** In `recall()`, before the conversation lane, query `scene` with the same OR-query through the same rarity gate.
